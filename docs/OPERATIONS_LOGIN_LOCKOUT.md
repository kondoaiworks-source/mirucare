# ログインアタック防止（ロックアウト）— 本番動作確認手順

この文書は、**本番（Vercel）環境**で「パスワードを連続で間違えると約15分ログインできなくなる」機能が動いているかを、専門知識がなくても確認できるようにしたものです。

**所要時間の目安**：15〜25分（15分待ちを含める場合は最大約40分）

---

## いま何を確認するか（1分で）

| 確認したいこと | 期待する結果 |
|----------------|--------------|
| わざと失敗を重ねる | **5回目**でロックされ、専用メッセージが出る |
| ロック中に正しいパスワード | **入れない**（同じ制限メッセージ） |
| 15分経過、または手動解除 | 再びログインできる |
| 監査ログ | `auth_audit_log` に記録が残る |
| 事業所admin / 運営(ops) | 設定画面からロックを解除できる |

---

## 始める前の準備

### 必要なもの

1. **本番アプリのURL**（Vercel の本番ドメイン。例: `https://あなたの本番ドメイン`）
2. **Supabase Dashboard**（本番プロジェクト）へのログイン権限
3. 次のアカウント（できるだけ「本番運用の本人アカウント」以外で）

| 役割 | 用途 | メモ |
|------|------|------|
| **テスト用ユーザー**（A） | わざと失敗させてロックさせる相手 | 事業所の staff でも admin でも可。メールアドレスを控える |
| **解除用ユーザー**（B） | ロック解除を試す人 | **同一事業所の admin**、または **運営(ops)**。A とは別アカウント必須 |

> **なぜ別アカウントが必要か**  
> A をロックすると、A 自身では設定画面に入れません。解除は B でログインして行います。

### やってはいけないこと

- 本番の「唯一の管理者」だけをロックして、解除用アカウントを用意しないこと
- 他人の本番アカウントで試すこと
- 確認中にパスワードを何度も変えて混乱させること（テスト中は変えない）

### 画面上のメッセージ（正解）

| 状況 | 画面に出る文言 |
|------|----------------|
| 1〜4回目の失敗 | `メールアドレスまたはパスワードが正しくありません。入力内容をご確認ください。` |
| 5回目以降・ロック中 | `ログイン試行が制限されています。しばらく時間をおいてから再度お試しください（約15分）。管理者に解除を依頼することもできます。` |

---

## Step 0：開始前にロックをクリアする（推奨）

過去の試験でカウンタが残っていると、回数の数え方がずれます。  
Supabase → 左メニュー **SQL Editor** → New query で、次を実行します（メールを差し替え）。

```sql
-- 確認だけ（今の状態を見る）
SELECT
  u.email,
  p.failed_login_attempts,
  p.lockout_until
FROM auth.users u
JOIN public.profiles p ON p.id = u.id
WHERE lower(u.email) = lower('テスト用ユーザーAのメール@example.com');
```

カウンタが 0 でない、または `lockout_until` に時刻が入っている場合は、**設定画面の解除**か、後述の「手動解除（SQL）」でクリアしてから本試験に進んでください。

---

## Step 1：わざと失敗させて、5回目でロックする

1. ブラウザの**シークレットウィンドウ**（または別ブラウザ）を開く  
2. 本番のログイン画面を開く  
   - `https://あなたの本番ドメイン/login`
3. **テスト用ユーザー A** のメールを入れる  
4. **わざと違うパスワード**を入れて「ログイン」する  

### 1〜4回目

- 毎回、上表の「失敗」メッセージが出ること  
- ログインできないこと  

回数を見失わないよう、紙やメモに「1」「2」…と書いてください。

### 途中経過の確認（任意・推奨）

3回目あたりで、Supabase SQL Editor で同じ確認クエリを実行します。

```sql
SELECT
  u.email,
  p.failed_login_attempts,  -- ここが 1,2,3… と増えているはず
  p.lockout_until           -- まだ NULL のはず
FROM auth.users u
JOIN public.profiles p ON p.id = u.id
WHERE lower(u.email) = lower('テスト用ユーザーAのメール@example.com');
```

- `failed_login_attempts` が失敗回数どおり増えていれば OK  
- `lockout_until` は **4回目までは空（NULL）** が正しいです

### 5回目

1. 同じく**誤ったパスワード**で5回目を実行する  
2. 画面に **「ログイン試行が制限されています…（約15分）」** が出ること  

SQL でも確認します。

```sql
SELECT
  u.email,
  p.failed_login_attempts,  -- 5 以上
  p.lockout_until           -- 未来の時刻が入っている
FROM auth.users u
JOIN public.profiles p ON p.id = u.id
WHERE lower(u.email) = lower('テスト用ユーザーAのメール@example.com');
```

| 項目 | 期待値 |
|------|--------|
| `failed_login_attempts` | `5`（以上） |
| `lockout_until` | いまからおおよそ **15分後** の時刻（UTC表示のことが多い） |

ここまでできたら **「5回でロック」は合格**です。

---

## Step 2：ロック中は正しいパスワードでも拒否される

1. 同じログイン画面で、ユーザー A のメール＋**正しいパスワード**を入れる  
2. それでもログインできず、**ロック用メッセージ**（約15分の文言）が出ること  

> ポイント：ロック中は「パスワードが正しいかどうか」の前に弾かれます。  
> 「正しいのに入れない＝故障」ではなく、**仕様どおり**です。

ここまでできたら **「ロック中の拒否」は合格**です。

---

## Step 3：解除後にログインできることを確認する

次のどちらか一方で十分です。両方やる必要はありません。

### 方法A：15分待って自然解除（仕様どおりの確認）

1. `lockout_until` の時刻まで待つ（約15分）  
2. 正しいパスワードでログインする  
3. **ダッシュボード等に入れる**こと  

SQL で見ると、成功後はだいたい次のようになります。

```sql
SELECT
  u.email,
  p.failed_login_attempts,  -- 0 に戻っている
  p.lockout_until           -- NULL
FROM auth.users u
JOIN public.profiles p ON p.id = u.id
WHERE lower(u.email) = lower('テスト用ユーザーAのメール@example.com');
```

> 期限切れ直後の「1回目のログイン試行」で、期限切れロックが自動クリアされます。  
> 成功すればカウンタも 0 に戻ります。

### 方法B：手動解除してすぐ確認（おすすめ・短い）

**B-1. 画面から解除（事業所admin / 運営）** ← 本試験の本番ルート

1. **別のブラウザ／シークレット**で、解除用ユーザー B でログインする  
2. 左メニュー（またはナビ）から **設定**（`/settings`）を開く  
3. 「**ログインセキュリティ**」→「**ログインロック解除**」を見る  
4. ユーザー A が一覧に出ていること（表示名・マスクされたメール・失敗回数・解除予定時刻）  
5. 「**ロックを解除する**」を押す  
6. 「ログインロックを解除しました。」のような成功表示が出ること  
7. 一覧から A が消えること（「現在ロック中のユーザーはいません。」でも可）  
8. シークレット側に戻り、ユーザー A の**正しいパスワード**でログインできること  

権限の整理：

| 解除する人 | できること |
|------------|------------|
| 同一事業所の **admin** | 自事業所のロックユーザーだけ解除可 |
| **運営（ops）** | 全事業所のロックユーザーを解除可 |
| **staff**（一般） | 設定に解除パネル自体が出ない |

**B-2. SQL で強制解除（画面が使えないときの非常手段）**

通常の `UPDATE` はガード（トリガー）で弾かれることがあります。  
次の順で実行してください（実行後は必ずトリガーを戻す）。

```sql
-- 1) 一時的にガードを外す
ALTER TABLE public.profiles DISABLE TRIGGER profiles_protect_login_lockout;

-- 2) ロック解除（メールを差し替え）
UPDATE public.profiles p
SET
  failed_login_attempts = 0,
  lockout_until = NULL
FROM auth.users u
WHERE p.id = u.id
  AND lower(u.email) = lower('テスト用ユーザーAのメール@example.com');

-- 3) 必ずガードを戻す
ALTER TABLE public.profiles ENABLE TRIGGER profiles_protect_login_lockout;

-- 4) 確認
SELECT u.email, p.failed_login_attempts, p.lockout_until
FROM auth.users u
JOIN public.profiles p ON p.id = u.id
WHERE lower(u.email) = lower('テスト用ユーザーAのメール@example.com');
```

**B-3. CLI（開発マシンから・任意）**

本番の Supabase **service role** が入った環境で:

```bash
npm run unlock-user -- --email=テスト用ユーザーAのメール@example.com
```

ここまでできたら **「解除後のログイン」は合格**です。

## Step 4：監査ログ（auth_audit_log）を確認する

Supabase SQL Editor で次を実行します。

```sql
SELECT
  action,
  email_masked,
  actor_profile_id,
  meta,
  created_at
FROM public.auth_audit_log
ORDER BY created_at DESC
LIMIT 30;
```

### いまの実装で「必ず」出るもの

| いつ | `action` | 見方 |
|------|----------|------|
| 5回目失敗でロックしたとき | `login_lockout` | `email_masked` が A のマスク（例: `te***@example.com`）。`meta` に失敗回数・解除予定など |
| 設定画面や CLI で解除したとき | `login_unlock` | `actor_profile_id` に解除した人（B）の ID。`meta.by` が `org_admin` または `operator` |
| 失敗履歴がある状態でログイン成功したとき | `login_success_reset` | 成功ログインでカウンタを戻した記録 |

### よくある誤解

- **1〜4回目の失敗ごとには、監査ログ行は増えません。**  
  回数は `profiles.failed_login_attempts` 側で持ちます。  
  （テーブル定義に `login_failed` という種類はありますが、現状の本番フローでは主に上記3種を見れば十分です。）
- メール全文は保存されません（ハッシュ／マスクのみ）。個人情報保護のための仕様です。

ここまでできたら **「監査ログ」は合格**です。

---

## Step 5：事業所admin / 運営による解除の再確認（チェックリスト）

すでに方法Bでやっていれば、ここはチェックだけです。

### 5-1. 事業所 admin

- [ ] ユーザー A を再度ロックする（誤PW×5）  
- [ ] 同一事業所の **admin（B）** で `/settings` → ログインロック解除  
- [ ] A を解除できる  
- [ ] `auth_audit_log` に `login_unlock`（`meta.by` = `org_admin`）がある  

### 5-2. 運営（ops）※運営アカウントがある場合

- [ ] 別ユーザーをロックする（または A を再ロック）  
- [ ] 運営アカウントで `/settings` → 同じパネルから解除できる  
- [ ] `auth_audit_log` に `login_unlock`（`meta.by` = `operator`）がある  

### 5-3. staff では解除できないこと（任意）

- [ ] 一般スタッフで `/settings` を開くと、「ログインセキュリティ」セクションが**出ない**  

---

## 合格判定まとめ

すべて Yes なら本番確認完了です。

| # | 確認項目 | OK? |
|---|----------|-----|
| 1 | 誤PWで 1〜4回は「正しくありません」系メッセージ | |
| 2 | 5回目でロックメッセージ、`lockout_until` が入る | |
| 3 | ロック中は正しいPWでも入れない | |
| 4 | 15分経過 **または** admin/ops 解除のあと、正しいPWで入れる | |
| 5 | `auth_audit_log` に `login_lockout`（と解除時は `login_unlock`）がある | |
| 6 | 事業所admin（または運営）が設定画面から解除できる | |

---

## うまくいかないとき

| 症状 | よくある原因 | 対処 |
|------|--------------|------|
| 何回失敗してもロックされない | 本番Vercelが古いデプロイ／マイグレーション未適用 | デプロイ済みか確認。`lookup_login_lockout` と列の有無を SQL で再確認 |
| 失敗しても `failed_login_attempts` が増えない | メールが未登録、または別環境のDBを見ている | ログイン先の本番Supabaseか確認。登録済みメールで試す |
| 設定に解除パネルがない | staff で見ている／admin・ops ではない | 事業所 admin または運営でログイン |
| 解除しても入れない | 別タブでまだ古い状態／PW誤り | シークレットを開き直し、正しいPWで再試行 |
| SQL の UPDATE が効かない | ガード用トリガー | 上記「B-2」の DISABLE → UPDATE → ENABLE を使う。終わったら必ず ENABLE |

---

## 試験後の片付け

1. テスト用ユーザー A がロック残りのままなら解除する  
2. 可能なら正しいパスワードで1回ログインし、カウンタが 0 であることを確認する  
3. 試験用にパスワードを変えていた場合は、運用ルールに従って戻す
